Análisis de Precisión de Tipos en el Cálculo de Fibonacci (precision.c)

El algoritmo precision.c calcula el número de Fibonacci para cada elemento de un arreglo
de tamaño N, comparando dos enfoques:

1. Cálculo Iterativo (Integer): f(n) = f(n-1) + f(n-2) con precisión exacta
2. Cálculo Basado en Número Áureo (Floating Point):
   φ = (1 + √5) / 2
   f(n) = (φ^n - (1-φ)^n) / √5
   Comparado en precisión simple (float) y doble (double)

Resultados de Tiempos de Ejecución (N = 1000000)
-------------------------------------------------
| Tipo de Dato             | Tpo. áureo (s) | Tpo. iterativo (s) | Error Medio  |
|--------------------------|----------------|--------------------|--------------|
| Precisión Simple (float) | 0.08           | 0.02               | 17.552436    |
| Precisión Doble (double) | 0.07           | 0.02               | 0.000000     |

Nota: el cálculo iterativo (int) es ~4x más rápido que la fórmula áurea porque evita
las costosas operaciones pow() y sqrt() de la FPU. El error medio se calcula con fabs().

¿Qué conclusiones se pueden obtener a partir de los tiempos de ejecución
y la precisión en los tipos de dato de coma flotante?

1. **Precisión Simple (float - 32 bits)**:
   - Mantiene ~7-8 dígitos decimales significativos
   - Para N > 50, comienza a perder precisión notoriamente
   - Para N > 70, los errores se vuelven inaceptables (errores relativos > 1%)
   - Causas:
     * Mantisa de solo 24 bits efectivos
     * Exponente limitado
     * Acumulación de errores de redondeo en la fórmula

2. **Precisión Doble (double - 64 bits)**:
   - Mantiene ~15-17 dígitos decimales significativos
   - Precisa hasta aproximadamente N = 80-85
   - Para N > 90, comienza a ver problemas de overflow en el tipo base
   - Mejor relación precisión/velocidad que float para este problema
   - Causas:
     * Mantisa de 53 bits efectivos
     * Mayor exponente (rango más amplio)
     * Errores de redondeo menores

3. **Rendimiento**:
   - Fórmula áurea (float y double): ~4x más lenta que la iterativa
   - El cuello de botella es pow()/sqrt(), no la precisión del tipo
   - Float y double tienen tiempos similares (latencia FPU similar para ambos)
   - Iterativa (Integer): más rápida Y más precisa para este problema

4. **Trade-off Precisión vs Velocidad**:
   - Para N < 50: float es suficiente y más rápido
   - Para 50 < N < 85: double es necesario (float pierde precisión)
   - Para N > 85: ambos tipos flotantes fallan; se necesita:
     * Aritmética de precisión arbitraria (libgmp)
     * Tipos de 128 bits o emulación por software
     * Métodos alternativos (matrices, etc.)

5. **Implicaciones Prácticas**:
   - Los tipos de coma flotante NO son adecuados para cálculos que requieren
     precisión exacta en valores muy grandes
   - La compensación por el cálculo directo (sin iteración) es válida solo para N < 50
   - Para aplicaciones científicas, es crítico entender las limitaciones de cada tipo
